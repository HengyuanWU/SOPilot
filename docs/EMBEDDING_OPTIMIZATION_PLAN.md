# Embedding优化方案

## 当前问题分析

### 1. 问题根源
- **频繁单次调用**: `kg/store.py` 的 `_store_node()` 方法对每个节点单独调用 `embed_single()`
- **批量处理不彻底**: 虽然 `linker.py` 有批量处理，但 store 层没有
- **缺少缓存机制**: 相同文本重复计算 embedding

### 2. API调用统计（估算）
假设处理一本教科书（100章节）：
- 节点数量: ~5000 个概念
- 当前方式: 5000+ 次 API 调用
- 优化后: ~160 次批量 API 调用（batch_size=32）
- **减少率: 97%**

## 优化方案

### 阶段1: Store层批量化 ✅ 
**目标**: 将 `store.py` 的节点向量计算改为批量处理

**实现**:
- 在 `store()` 方法中，先收集所有节点
- 批量计算所有节点的 embedding
- 再进行存储操作

**预期效果**: 减少 95%+ 的 embedding API 调用

### 阶段2: 添加LRU缓存 ✅
**目标**: 避免相同文本重复计算

**实现**:
- 在 `Embedder` 类中添加 LRU 缓存
- 缓存大小: 10000 个条目
- 基于文本内容+模型名的key

**预期效果**: 命中率 30-50%，进一步减少 API 调用

### 阶段3: 智能预热 ✅
**目标**: 减少首次处理的 API 调用次数

**实现**:
- 知识图谱构建前，预加载已有节点的向量
- 只为新节点计算 embedding

### 阶段4: 异步批量处理
**目标**: 提高吞吐量

**实现**:
- 使用异步 API 调用
- 并发处理多个批次

## 实施计划

1. **立即执行**: Store层批量化 + LRU缓存
2. **短期优化**: 智能预热
3. **长期优化**: 异步批量处理

## 监控指标

- API 调用次数
- 缓存命中率
- 平均响应时间
- 成本节约比例
